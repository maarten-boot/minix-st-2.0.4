## Follow-up 67: the kernel panic on a user program's bus error

* **Cause:** not the kernel's exception code (a user fault does become a
  signal), but MAME's 68010 (Musashi), which raises a bus error one
  instruction late:
  * a user program jumps to nonexistent memory (a return address smashed
    by an overrun: the old shutdown; finger's `&&&&` = 0x262626);
  * the opcode fetch reads 0x00FF, an illegal instruction: a format 0
    frame from user mode, into illtrp;
  * only then the bus error arrives, at illtrp's first instruction, in
    supervisor mode (illtrp is at 0x219e, the pc of the report), and
    trap() (roscmain.c) panics on a supervisor-mode fault.
  * A data fault just before a trap #0 or an interrupt lands the same
    way.
* The 68010 frame handling was checked and is right: a user fault's
  29-word format 8 frame is dropped (restart builds a format 0 frame),
  framesizes[8] is 62 for supervisor faults.
* **Fix** (`src/kernel/roscompx.S`, buserr on a 68010 → berr010): a
  format 8 frame from supervisor mode whose pc is the handler entry of
  the format 0 user-mode frame right above it is the user's bus error;
  the bus error frame is dropped and it goes to gentrp with the user
  frame. A real 68010 never matches; every other supervisor-mode bus
  error still panics.
* Tested in MAME with a fault test program (jumps, reads and writes to
  nonexistent memory, odd pc and sp, illegal instructions, a stack smash
  with "&&&&"):
  * before: `flt j` (jump to 0xd00000) → "kernel trap: pc=219e ... Kernel
    panic: trap via vector 2";
  * after: "Memory fault - core dumped" (status 139) for the jumps, the
    stack smash and an sp in nonexistent memory; an odd sp gives signal
    10; the others as before; the system keeps running.
* Notes:
  * SIGBUS is 10 (= SIGUSR1) in Minix, so address errors show "User
    signal 1", as on the ST;
  * MAME's 68010 gives no address error for odd data accesses (odd pc
    does trap);
  * no memory protection: a stray user write can still corrupt the
    kernel;
  * the real fix belongs in MAME (assert BERR synchronously); not done.
  * The kernel build runs `make kernel.bin` on the host (it calls ../xrun
    itself).

## Follow-up 68: INET: a cancelled listen; tcpd reaps at once again

* **Cause** (src/inet/generic/tcp.c tcp_cancel): a cancelled
  NWIOTCPLISTEN (tcpd's SIGCHLD) that had already answered a SYN
  (SYN_RECEIVED) closed the connection without telling the client; the
  client's bare ACK of the SYN-ACK gets no RST from a closed connection
  (create_RST), so a client waiting for the server (ftp, telnet) hung
  forever, and one that speaks first (rsh, rlogin) got a RST on its first
  data: the "reset within about 1 s" of Follow-up 63 is the same bug.
* **Fix** (fixed copies `src/rosco/boot/inetfix/generic/tcp.c`,
  `tcp_recv.c`, rules in boot/Makefile): such a connection is kept
  without a user (an orphan); the next listen on the same port takes it
  over (find_orphan: SYN_RECEIVED or already ESTABLISHED, honouring the
  listen's remote address and port); closing the channel without
  listening again closes its orphans. A cancelled listen without a SYN
  and a cancelled connect are closed as before.
* **tcpd** (fixes/simple/tcpd.c.patch): SIGCHLD is unblocked during the
  listen again, so finished servers (in.rshd) are reaped at once; the
  trade-off of Follow-up 65 is gone.
* Tested in MAME over SLIP with a Python helper logging every segment:
  * a raw SYN, `kill -CHLD` of tcpd, then the ACK: ftp and telnet got no
    answer → the greeting; an ACK with data got a RST → served;
  * 10 quick sequential ftp and telnet connections: every other one
    hung → all served; parallel, staggered, reset and same-port
    reconnects all fine; no zombies afterwards.
* **Open: ports below 1024 for any user.** INET cannot know the caller's
  uid: FS passes no uid in its device messages. Needed: FS passes
  fp_effuid (e.g. in POSITION of DEV_IOCTL, unused by other drivers),
  INET's sr.c keeps it per request, and tcp_setconf and NWIOSUDPOPT
  refuse a local port below 1024 to non-root (EACCES), explicit or
  chosen by NWTC_LP_SEL.
* Notes: a listen on another channel of the same port could take and
  close an orphan after its quiet time (rare); the board picks the same
  ISS for a reused 4-tuple; after closing first it answers the peer's FIN
  with a RST.

Committed `9405fdc` (B).

## Follow-up 69: INET psip: an oversized packet killed SLIP

* **Cause** (src/inet/generic/psip.c psip_send): a packet bigger than
  slip's 2048-byte read (`ping host 3000`, ping is setuid root) was
  answered with EPACKSIZE but kept at the head of the queue, so every
  later read failed and slip exited ("Invalid packet size"). INET does
  not fragment for psip at all.
* **Fix** (fixed copy `src/rosco/boot/inetfix/generic/psip.c`, rule in
  boot/Makefile): the packet is dropped and the reader stays queued
  without an error.
* Tested in MAME over SLIP: before, `ping host 3000` ended slip and all
  later pings failed; after, it gets no answer and slip, `ping host`,
  1000 and 1200 work on.
* **The 1500-byte ping** (Follow-up 62): not INET. Hand-made fragments
  0.3 s apart are reassembled and answered (1300, 1500); back to back,
  1300 bytes and more are lost in the 1024-byte tty00 input buffer
  (RS_IBUFSIZE) at 115200: RTS does not throttle the emulated peer.
* **Open, serious: a remote INET panic.** A ping of 2000 bytes or more
  from the host, in fragments (Linux does that itself with `ping -s 2000`
  over MTU 296), halts the board: `panic at ../../inet/buf.c, 429`
  (bf_dupacc, out of accessors), with the original INET too. 1800 bytes
  (7 fragments) is answered, 2000 (8) panics. Likely the small CRAMPED
  pools (BUF512_NR 32, ACC_NR 48, inet/buf.c) used up by the fragments
  in reassembly and the copies for the ICMP reply.
* Notes: the same EPACKSIZE pattern is in promisc_restart_read (not used
  by slip); outgoing IP packets over 2048 bytes are now dropped
  silently, not fragmented.

## Follow-up 70: INET: a remote host could panic it with fragments

User:
> ok fix the INET fragment panic first

* **Causes** (three, all reachable from the network):
  * **out of accessors** (inet/buf.c:429 bf_dupacc): the CRAMPED pools
    have 32 buffers and 48 accessors, and every buffer ties up one
    accessor, so 16 are spare. A reassembled packet comes with one piece
    per fragment, and ICMP cuts it twice (icmp.c process_data and
    icmp_echo_request), about 2 spare accessors per piece, which nothing
    can free while the packet is in hand: 7 fragments (1800 bytes) were
    answered, 8 (2000) panicked;
  * **a leak in reassembly** (ip_read.c reassemble): a fragment that fit
    between two others without touching the one before it was linked
    after it and then overwritten by the link to the next one; fragments
    0, 4, 2 of a few dozen packets used up all buffers: `panic at
    ../../inet/buf.c, 295`;
  * **duplicates** (merge_frags): a fragment lying inside the piece
    before it replaced that piece, so the packet never completed.
* **Fix** (fixed copy `src/rosco/boot/inetfix/generic/ip_read.c`):
  * a packet in reassembly may hold at most 16 accessors (16 fragments
    of MTU 296, about 4 kB); one more drops the whole packet;
  * a new fragment is merged with the ones after it first, then with
    the one before it;
  * a duplicate is dropped instead of the piece it lies in.
* **Pools:** inet/buf.c is built with `-DBUF512_NR=120` (180 accessors, 60
  spare; 128 would take the buffer array past 64K). INET grows from
  119600 to 168212 bytes. Bigger pools alone are not enough: without the
  limit, 26 fragments were answered and 30 panicked.
* Tested in MAME over SLIP with a raw fragment sender in the container:
  * original: 2000 bytes → panic (buf.c 429); 60 trains of fragments 0,
    4, 2 → panic (buf.c 295);
  * fixed: 1800, 2000, 2048 answered; 3000 reassembled but its reply is
    dropped by the psip fix; 4500, 8000 and 65535 dropped by the limit;
    20 incomplete trains, the 0/4/2 trains, duplicates (now answered), a
    flood of 50 pings and 8-byte fragments all survived; afterwards
    ping both ways and the ftp greeting through tcpd still worked.
* Notes: INET does not fragment outgoing packets for psip (replies over
  2048 bytes are dropped); the time-exceeded messages for reused
  reassembly entries were not seen leaving the board (not investigated).

Committed `ff60c23` (E). Images rebuilt; smoke test (slip, ping, ping
3000, ttyp0, cron) fine.

## Follow-up 72: INET review I: buffers, the FS interface, the rest

* **Fixed** (fixed copies `inetfix/sr.c`, `inetfix/buf.c`):
  * **one user froze the whole system:** a protocol handler that
    returned an error (EFAULT for a bad ioctl address: tcp_setconf,
    tcp_setopt, udp_setopt) got no reply, because sr.c only expected OK
    or SUSPEND (its assert is compiled out), and FS waited in sendrec for
    good; sr.c now sends the error itself when the request is still
    unanswered (at the head of its queue, in progress), so it cannot
    answer twice; this covers queued requests too;
  * a cancel of a request INET did not have got no answer (FS hung);
    now EINTR;
  * an unknown message type got no answer; now EINVAL;
  * sr_open accepted minor FD_NR (one past the table);
  * sr_repl_queue read through m (NULL) instead of m_cancel;
  * **any user could panic INET:** a 16000-byte UDP write (out of
    accessors: the write's chain is duplicated twice on its way down,
    and only 60 of 180 accessors were spare); ACC_NR is now 360 (240
    spare, about 3K more memory), and single writes up to 32767 bytes
    work;
  * bf_memreq(0) wrote through an unset pointer.
* Tested in MAME over SLIP, original vs fixed: `ioctl(NWIOSTCPCONF, bad
  address)` as ast froze everything → EFAULT; EFAULT also for the other
  TCP/UDP option ioctls and UDP reads and writes; 16000-byte UDP write
  panic → fine up to 32767, 4×5 such writes in parallel; table full
  (EAGAIN) and reopening, 20 cancels, close during reads, 12 TCP
  connections writing to a peer that never reads; ping and the ftp
  greeting afterwards.
* Checked: stack -S 8k is enough (largest frame 212 bytes, measured);
  the ethernet/ARP files compile to nothing (ENABLE_ETH 0); asserts are
  off (NDEBUG), only ip_panic halts the board.
* Notes:
  * out of buffers, tcp_buffree closes in-use connections, so one user
    can kill other users' TCP connections (EOUTOFBUFS; design, no
    crash);
  * inet.c leaks an mq for messages from other sources than FS or the
    clock (only tasks and servers can send to INET);
  * clock ticks are signed: timers misbehave after 2^31 ticks (414 days
    at 60 Hz);
  * more than 4 lines in /etc/inet.conf overflow its tables (root only);
    alloc() does not check sbrk.
