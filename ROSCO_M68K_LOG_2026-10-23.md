## Follow-up 85: a lone ESC is passed on after a timeout (from 2026-10-21)

The entry of the old host, as it was:

* **Problem** (found by the BBC BASIC port): `cons_debug_key()` holds back
  an ESC until the next character shows whether a PF key (ESC O P..S)
  follows. A lone ESC, e.g. BBC BASIC's Escape key or vi's, therefore
  reached the program only at the next keypress.
* **Fix:**
  * `cons_debug_key()` starts a countdown of ESC_TICKS = 3 clock ticks
    (33..50 ms) for a held-back ESC or ESC O;
  * `kb_timer()` (each tick, until now a stub) counts it down; at 0 it
    sets `esctimeout`, marks tty 0 for events and calls
    `force_timeout()`;
  * `rs_read()` calls the new `cons_esc_timeout()` after the buffered
    characters, which passes the ESC (or ESC O) on. A PF key whose
    characters have already arrived is still recognised.
* **Tested** (old host):
  * r68k: Escape stops a running BBC BASIC program at once; PF1 still
    prints the process table; the BBC BASIC test suite (24 suites)
    passes;
  * MAME (CONSBAUD=115200): PF1, then Escape in a running
    `REPEAT ... UNTIL FALSE`, gives "Escape at line 10".

Tested again here (MAME, 115200, the old kernel of 2026-10-22 against
the new one, same root):
* `stty raw; dd bs=1 count=1 | od -b`, then ESC alone: old kernel
  nothing (the session timed out), new `0000000 033` at once;
* ESC, 2 s, `O` with `count=2`: new `033 117` (both passed on as

* PF1 (ESC O P in one go) still prints the process table;
* elvis: `ihello`, ESC, ESC, `:wq` one key a second: written, "hello".
* This is the kernel side of the elvis ESC/`:` report (Follow-up 83);
  the elvis `escbell()` fix stays needed for an ESC and `:` that arrive
  within 50 ms.

## Follow-up 86: sigreturn keeps the condition codes (from 2026-10-21)

The entry of the old host, as it was:

* **Problem** (found by the BBC BASIC port, whose ESCape is now a SIGINT
  from the console):
  * `do_sigreturn()` (system.c) restored every register from the
    sigcontext except the status register. It took that from the process
    as it was at the sigreturn call (`sc.sc_psw = rp->p_reg.psw`, there
    so that a user cannot set supervisor bits).
  * So the interrupted code resumed with the condition codes of the
    signal handler's exit, not its own. A signal between a compare and
    its branch changed where the branch went.
  * BBC BASIC failed about one run in four (Syntax error, lost state); C
    code compiled by ACK or gcc is exposed to it the same way.
* **Fix (M68000):** the supervisor byte stays as it is; the user's X N Z
  V C come from the sigcontext:
  `sc.sc_psw = (rp->p_reg.psw & ~0x1F) | (sc.sc_psw & 0x1F)`.
* **Tested** (old host) with the port's terminal test (ESCape signals
  during loops, GET, INKEY with *ESC OFF, after *commands): 20 of 20 runs
  pass, against about 3 of 4 before.

Added here: a regression test **`src/rosco/test/tsigcc.c`** (test
Makefile, `/usr/test/tsigcc` in sdproto): a child sends SIGUSR1 to the
parent as fast as it can, the parent runs 2000 × 10000 rounds of
`cmp`/`bne`, `cmp`/`beq`, `cmp`/`bcc` (Z set, Z clear, C set) and
counts the branches taken that must not be.
* Old kernel: "Test sigcc failed: 28 wrong branches, 466 signals, 2000
  loops"; new kernel: "Test sigcc ok".
