## Follow-up 81: a minimum stack of 8kw for every command

User:
> fix the 4kw stack problem in general first

* **Cause:** a Minix executable's arguments and environment (up to
  ARG_MAX, 4K), its heap and its stack all share the gap between the bss
  and the top of memory that chmem/-S sets. malloc grows the heap in 4K
  steps (BRKSIZE 4096 for 32-bit pointers) and stdio's buffers come from
  it; gcc's frames are bigger than ACK's (_doprnt alone has a 1K buffer).
  The ACK build's 4kw (8K) left no room: at, who, mail, passwd, cut,
  install and ifdef died one by one ("Memory fault", often without
  "Stack low"), and wc with a 1.2K environment.
* **Fix:** tools/mkminix.py has a new option `-m`, a minimum for `-S`;
  cmds/Makefile passes `-m 8kw` (16K) for every command. All 186
  commands rebuilt: none has a gap under 16K now. Cost: at most 8K more
  memory per running small command. The per-tool STACK_ settings of 8kw
  stay (they document the cases); boot/ and test/ are not affected.
* Tested in MAME (5MB): wc, cut, head, sed, grep, cat, sort, uniq,
  basename, date, id, tty, expr, od with a 1.2K environment, most of
  them and tr with 3.3K, wc with 3.8K: all exit 0, no Memory fault.

Committed `6f15c3a`. Then CLAUDE.md, working notes for Claude Code
sessions: committed `d1d6fec`.

* **elle** (fixes/elle/sbm.c, sbstr.c, eeerr.c, eefile.c, eebuff.c,
  eecmds.c, eemain.c patches):
  * the GC never swapped modified text out (sbstr.c:1724): sbm_nfor's
    prototype makes the level a 4-byte pointer, sbx_sdgc read its high
    half (always 0); uppercasing a 144K region and saving gave
    "SBXERR: 15" and endless garbage; now written correctly;
  * every SB error crashed elle (sbstr.c:2193, sbm.c:722, eeerr.c:42/60:
    a pointer passed as a 2-byte int, the format moved): "sig=11 …
    Memory fault"; now the message and C continues;
  * saving under a path of 100+ characters overran the stack (eefile.c,
    FNAMSIZ 100): sig=11; now 271, longer is "File name too long";
  * `^X=` counted lines in an int ("Line -25535"); now chroff;
  * `-p profile` fell through into "bad switch" (eemain.c:177);
  * sbm.c compared sbrk() results as 16-bit ints and could pass 32K+
    increments; set_profile overruns, NULL HOME, a long size cut to int.
* **ellec** (fixes/elle/ellec.c.patch): a profile line of 300+
  characters overran linebuf (Memory fault, status 139); lrstr one byte
  past cbuf; a long $HOME refused. The shipped defprf.e compiles and
  elle uses the result.
* **yap** (fixes/yap/main.c, getline.c, keys.c, commands.c patches):
  piped input of about 1 MB died with "No core" (block table in a 32K
  gap; now -S 64kw, and new_block panics instead of wrapping at 3276
  blocks); EOF on the command input spun forever (`yap f </dev/null`);
  a long $YAPKEYS overran ebuf[80] (yap became cat); `35000s` did
  nothing (long count cast to int); execve of cat with a NULL envp.
* **Stacks:** yap 16kw → 64kw, elle 64k → 128k (the heap reached the
  stack when saving after an edit of 50K+); ellec unchanged.
* Also tested: line 33000, `/MARK` and `?MARK` on 40000 lines, 5000-
  character lines, missing file, `man yap`, `ls -l /usr/bin | more`;
  all exit 0, no "Stack low", no signals with the final binaries.
* Not fixed: elle numeric arguments are int everywhere (Goto Line past
  32767); elle Debug Mode pointers cut; sbx_rdf's message has two
  garbage %ld; hoard() opens "nul:"; yap page counts 65536+, empty
  search without a pattern, rc_error never cleared.
* For the user (outside cmds): libc execve() reads *envp when envp is
  NULL; tools/mamesession.py chooses its port from the pid, so parallel
  sessions can collide (seen in run N6; bind port 0 instead).
